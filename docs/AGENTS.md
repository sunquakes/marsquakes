# Docs - AGENTS.md

## Module Overview

- **Type**: Documentation site — **not a platform**
- **Scope**: Public documentation for this project
- **Tech Stack**: Docusaurus 3 / TypeScript / MDX
- **Registered in**: `platforms.json` → top-level `docs` section (`site_dir: docs`)

This directory is not listed under `platforms.platforms` in `platforms.json`, and
that is intentional. A platform is a shippable application target; the
documentation describes the project rather than being one of its targets.
Consequences:

- `mars create` never offers Docs as a selectable module, and `mars dev` /
  `mars build` / `mars init` never touch it.
- It is not a pnpm workspace member, so `pnpm --filter docs` does not resolve
  and `turbo build` at the root does not include it. This keeps the heavy
  Docusaurus dependency tree out of the root `pnpm-lock.yaml`.
- Run its scripts from the repository root with `pnpm -C docs <script>`, which
  simply changes directory instead of going through workspace resolution. The
  root `package.json` exposes `pnpm dev:docs` as a shortcut for the dev server;
  it is a plain `pnpm -C docs dev`, deliberately **not** a `turbo` task.

## Critical Rule: `docs/` vs `.docs/`

The repository splits documentation by **audience**, not by format:

| Directory | Audience | Content |
|-----------|----------|---------|
| `docs/` (this directory) | Public | The Docusaurus site: config, sidebars, theme, i18n and the published pages in `docs/content/` |
| `.docs/` (repository root) | Internal | Program design documents, PRDs, task breakdowns and API interface documents. Never published, never referenced by the site |

Consequences you must respect:

- A page is published **only** when it lives in `docs/content/` **and** its `id`
  is listed in `sidebars.ts`. Sidebars are explicit (not `autogenerated`) so
  that publishing is always a deliberate decision.
- Never put design drafts, PRDs, task notes or API interface documents in
  `docs/` — they belong in `.docs/`. See the root `AGENTS.md` Work Mode rules.
- Site configuration files stay at the top level of `docs/`; only Markdown pages
  go inside `docs/content/`. This is why `docusaurus.config.ts` sets
  `path: './content'` rather than using the Docusaurus default.

## Routing

`src/pages/` and the docs plugin share one route namespace, so they must not
collide:

- `/` is the landing page, `src/pages/index.tsx`.
- Every published Markdown page is served under `/docs`, because
  `docusaurus.config.ts` sets `routeBasePath: '/docs'`. Do not set it back to
  `'/'` while the landing page exists — the build fails on a duplicate route.
- `content/intro.md` keeps `slug: /`, which resolves *relative to the base path*
  and therefore lands on `/docs`, making it the docs section index.
- Relative links between Markdown pages (`./cli.md`) are rewritten automatically.
  Only absolute link targets — footer `to:` entries, `href`s inside components —
  need the `/docs` prefix written out by hand.

## Internationalisation

`defaultLocale` is `en`; `zh-Hans` is the second locale, surfaced through a
`localeDropdown` navbar item.

- Translated Markdown must **mirror the English filename and front-matter `id`**
  under `i18n/zh-Hans/docusaurus-plugin-content-docs/current/`. Note that the
  translation tree mirrors the contents of `content/`, so it has no extra
  `content/` level. A missing file silently falls back to English.
- Translation files are split by **owner**, and putting a key in the wrong file
  fails silently — the string simply renders in English:

  | File | Owns |
  |------|------|
  | `code.json` | Strings from React components, i.e. every `<Translate>` / `translate()` call in `src/pages/` |
  | `docusaurus-theme-classic/navbar.json` | Navbar title, logo alt, item labels |
  | `docusaurus-theme-classic/footer.json` | Footer column titles and link labels |
  | `docusaurus-plugin-content-docs/current.json` | Sidebar category labels |

- Never hard-code prose in `src/pages/`. Wrap it in `<Translate>` with an
  explicit `id` so it can be extracted.
- Regenerate the translation stubs after changing navbar/footer/categories or
  after adding component strings:

```bash
pnpm -C docs write-translations --locale zh-Hans
```

  Then prune the result: the command writes ~115 untranslated theme defaults into
  `code.json`, adds a `version.label` to `current.json`, and freezes the current
  year into `footer.json`'s `copyright`. Keep only the keys this project actually
  overrides — **an omitted key falls back to the source value**, which is exactly
  what the dynamic `new Date().getFullYear()` copyright needs.

## Build Commands

Run from this directory. It is a standalone package — it is not a pnpm workspace
member and the root pnpm scripts do not proxy to it.

```bash
cd docs

pnpm install
pnpm dev                      # Dev server (English)
pnpm dev -- --locale zh-Hans  # Dev server (Simplified Chinese)
pnpm build                    # Static build into docs/build
pnpm serve                    # Serve the production build locally
pnpm clean                    # Clear the .docusaurus cache
pnpm type-check               # tsc --noEmit
```

## Coding Standards

- **Node >= 22.12.0** is required, which is the repository-wide floor declared in
  every `package.json`, in `.nvmrc` and in the root `volta` pin. Docusaurus 3
  itself only asks for `>= 20`, but Vite 7 elsewhere in the monorepo needs
  `20.19+` or `22.12+`, so the whole repo is unified on one number rather than
  each package carrying its own. Keep the `engines` field accurate.
- **Code comments are written in English**, including `docusaurus.config.ts`,
  `sidebars.ts` and `custom.css`.
- `onBrokenLinks` is `throw`. A dead relative link fails the build — always run
  `pnpm build` before committing content changes.
- Prefer Docusaurus admonitions (`:::note`, `:::warning`, `:::tip`) over bold
  paragraphs for callouts.
- `.md` files are parsed as MDX, so a bare autolink such as `<user@example.com>`
  is read as a JSX tag and breaks the build. Use an explicit `mailto:` link.
- When a Markdown example itself contains a fenced block, wrap the outer fence
  in **four** backticks so the inner fence does not terminate it early.
- Theme colours come from Infima CSS variables in `src/css/custom.css`. Override
  variables rather than hard-coding colours in components.
- Components in `src/pages/` style themselves with a co-located CSS Module
  (`*.module.css`) that consumes those same Infima variables, so a palette change
  in `custom.css` propagates everywhere and dark mode keeps working for free.

## Deployment

The site is published to **GitHub Pages** on the custom domain
**`marsquakes.cc`**. The repository itself stays under the `sunquakes`
organisation, so `organizationName` / `projectName` and every GitHub link
(`editUrl`, the navbar item) point at `sunquakes/marsquakes` while `url` points
at the domain. Those two are independent — do not "fix" one to match the other.

The domain is declared in **two** places, and both are required:

| Place | Consumed by | If it is wrong |
|-------|-------------|----------------|
| `url` in `docusaurus.config.ts` | Docusaurus, for absolute URLs in the sitemap, canonical tags and social metadata | The site still serves, but crawlers and shared links point at the old host |
| `docs/static/CNAME` | GitHub Pages, on every deploy | The deploy resets the custom domain and the site falls back to the `github.io` host |

`static/CNAME` is copied verbatim into the build output, which is exactly how
GitHub Pages expects the domain to be committed. It must contain the bare
hostname, no scheme and no trailing path, and be **LF-terminated with no BOM** —
a BOM makes Pages read three invisible bytes as part of the hostname and the
domain silently stops resolving.

`baseUrl` is `/`, so routes are served from the domain root (`/docs/cli`). That
is correct for a custom domain or a `<org>.github.io` **user** site. A GitHub
Pages **project** site serves from `/<repo>/` instead, so publishing there
requires setting `baseUrl` back to `/marsquakes/` — otherwise every asset and
link resolves one directory too high and the site loads without CSS. Never
hard-code the prefix into a link to work around this: use relative `.md` links
in content and `to:` (not `href:`) in the config, both of which Docusaurus
rewrites with whatever `baseUrl` is in effect.

The one place the domain is unavoidably hard-coded is the skill download command
on the `ai-setup` pages (both locales): the reader runs `curl` before they have
a checkout, so it cannot be a relative link. Update those two pages whenever the
domain changes — `pnpm -C docs build` cannot catch a stale absolute URL.

Build output goes to `docs/build`, which is gitignored by exact path — a bare
`build/` rule is deliberately avoided because `apps/web-admin/build/` is tracked
source.
